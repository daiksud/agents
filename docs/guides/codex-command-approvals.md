## Codexのコマンド事前許可

### 🔑 承認と表示の違い

| 対象 | 役割 |
| --- | --- |
| 計画の承認 | 変更、コミット、PR、レビュー対応、マージまでの作業範囲を合意する |
| サンドボックスの権限 | ファイルへの書き込みやネットワーク接続など、実行可能な範囲を定める |
| コマンドの許可ルール | 一致するコマンドをサンドボックス外で実行する際の承認要求を制御する |
| ツール実行表示（Call） | アプリが操作を表示する。許可ルールは表示を非表示にする設定ではない |

計画の承認だけでは環境の権限は増えません。関連する確認をまとめればCallの回数は減らせますが、利用環境に表示制御がなければ非表示にはできません。

`Would you like to make the following edits?` のような編集確認は、実行表示に加えて操作の承認を求める画面です。承認済みの計画に含まれるファイル編集や一時ファイル作成でも、実行環境が確認を要求する場合があります。エージェントの再確認と環境側の承認を区別し、表示された許可の対象範囲を確認します。「これらのファイルでは次回から確認しない」は、すべての編集を許可する選択ではありません。以下のコマンドルールだけで編集ツールの確認も消えるとは扱いません。

### 📋 計画時に確認すること

1. 作業ルート、Git管理領域、一時ファイル、検証の出力先への書き込み権限を確認します。作業ルート内でも `.git` などが保護される場合があります。
2. GitHubへの接続と認証、依存関係の取得など、必要なネットワーク接続を確認します。
3. 次の操作から、そのタスクに必要なコマンドと引数を洗い出し、既存の許可と照合します。
4. 不足分について、環境が提供する承認画面での許可保存、または以下のルール設定を準備します。

| 操作 | コマンド例 |
| --- | --- |
| ブランチと履歴 | `git switch -c`、`git fetch origin`、`git rebase origin/main` |
| 変更の保存と送信 | `git add`、`git commit`、`git push`、必要時の `git push --force-with-lease` |
| Issue | `gh issue create`、`gh issue edit`、`gh issue comment` |
| PR | `gh pr create`、`gh pr view`、`gh pr checks`、`gh pr ready`、`gh pr merge --squash` |
| レビュー | `gh api` によるレビュー依頼、返信、スレッド解決 |
| 検証 | プロジェクトで定められたテスト、lint、ビルドコマンド |

この表は一括許可リストではありません。対象のリポジトリ、引数、書き込み範囲を確認し、タスクに必要なコマンドだけを選びます。特に `gh api` はAPIの操作範囲が広いため、具体的なエンドポイントやGraphQL操作も確認します。

### ⚙️ 許可ルールの準備

利用者が `~/.codex/rules/task-lifecycle.rules` など、アクティブな設定階層の `rules/` 配下にルールを配置します。既存のルールは保持し、タスク指示だけで設定済みとは扱いません。

次は、PRの状態取得を許可する最小の例です。他の操作には、その操作に対応した別の許可が必要です。

```python
prefix_rule(
    pattern = ["gh", "pr", "view"],
    decision = "allow",
    justification = "PRの状態確認を事前許可する",
    match = ["gh pr view 3 --json state"],
    not_match = ["gh pr merge 3 --squash"],
)
```

- `allow` は一致するコマンドのサンドボックス外実行を承認要求なしで許可します。`prompt` は承認要求、`forbidden` は拒否です。
- 複数ルールに一致した場合は、`forbidden`、`prompt`、`allow` の順に厳しい判断が優先されます。
- コマンド先頭からの一致なので、オプションの位置やラッパーを変えると一致しない場合があります。
- シェルやインタープリター全体を許可せず、必要なサブコマンドに絞ります。破壊的操作を汎用の許可に含めません。
- コマンドをまとめても個別の権限確認は省略できません。変数展開、リダイレクト、コマンド置換などは、単純なコマンド列と同じ方法で分解・照合されない場合があります。
- 権限昇格が必要な `gh` と、通常権限で実行できる `cat` などは別々に実行します。まとめて昇格すると、ローカル読み取りにも追加の許可を求める原因になります。既存の許可を確認し、通常権限で実行できる操作まで昇格しません。

設定を保存したらCodexを再起動します。プロジェクトの `.codex/rules/` を使う場合、その設定階層が信頼されている必要があります。承認画面で保存する許可の挙動は、利用するアプリ・バージョンで確認します。

> [!IMPORTANT]
> 管理者の制限や実行環境のポリシーは優先されます。事前許可を準備しても、追加の承認が不要になるとは保証できません。エージェントは適用される制限を回避しません。

### ✅ ルールの検証

```bash
codex execpolicy check --pretty --rules ~/.codex/rules/task-lifecycle.rules -- gh pr view 3 --json state
codex execpolicy check --pretty --rules ~/.codex/rules/task-lifecycle.rules -- gh pr merge 3 --squash
```

この例のファイルだけを指定した場合、1つ目は `allow` と一致したルールが表示され、2つ目は一致するルールがないことを確認します。未一致は明示的な拒否と同義ではありません。複数の設定を確認する場合は `--rules` を繰り返して指定します。

この検査はコマンドを実行せず、指定したルールの照合を確認します。アプリへの読み込み、認証、ファイル権限、ネットワーク接続は別に確認します。再起動後、事前許可した読み取り操作で承認要求の有無を確認します。
