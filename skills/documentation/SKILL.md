# 読者に必要なドキュメントを整える

読者が必要な情報を理解し、目的を達成できる文書を書く。対象リポジトリの言語・用語・規約と、依頼された変更範囲に従う。

開発者向けでは、そのリポジトリを初めて担当する人が構造とルールを理解し、変更・検証・保守を進められることを目標にする。

## 基本方針

- 読者を文書の利用目的で分ける。APIやライブラリを使うエンジニアは利用者、プロダクトを変更・保守する人は開発者として扱う。
- 利用者向けは `docs/concepts.md`、`docs/tutorials.md`、`docs/guides.md`、`docs/references.md` に分類する。開発者向けは文書の種類によらず `docs/development/` にまとめ、現在の開発方針は `docs/development/policies.md` に書く。
- 各文書は必要になった時点で単一ファイルから始める。内容が増えて話題を分ける必要が出たら、同名のディレクトリを作って分割する。分割後も必要に応じて階層を深くする。各機能に全種類のページ、空のディレクトリ、専用の計画書を一律に作らない。
- 現在の理解や作業に必要な情報を書く。仕組みの目的や理由は必要に応じて含め、採用・変更時の比較や経緯はPR・コミットに残す。
- 仕様は実装・スキーマなどの定義元と揃える。背景や仕様の詳細は参照先にまとめ、ガイドの作業に必要な操作手順はそのページで読めるようにする。

## 作業の進め方

1. 依頼の目的、既存の文書、仕様の定義元、リポジトリの指示を確認する。読者の質問や既存のIssueなど、使える根拠から不足を把握する。
2. 読者の前提知識、達成したいこと、読後に理解・実行できることを決める。[配置の指針](references/placement.md)で文書の種類と配置を選ぶ。
3. [執筆の指針](references/writing.md)に従い、主な目的を絞って構成する。必要な前提、説明、手順、結果を揃えてから表現を整える。
4. 現在の説明に必要な出典を、その説明の近くに示す。外部の仕様と独自の方針、確認した事実と未確認の事項を区別する。
5. 正確さ、必要な内容、構成、明確さ・簡潔さを確認する。読者が理解や作業を進められるかを確かめ、既存のMarkdown・リンク検査や必須チェックに従う。
6. 影響する文書、例、目次、リンクを同じ変更で更新する。実行による確認、静的な確認、未確認の範囲を区別して報告する。

配置の整理だけを依頼された場合は、その範囲を扱う。軽微な修正では既存の目的と構成を活かし、変更に必要な確認を行う。

## 詳細を読むとき

| 判断すること | 参照先 |
| --- | --- |
| 読者の区分、配置、開発者向けの話題、共有する仕様、実行指示と保守資料、出典文書の整理 | [配置の指針](references/placement.md) |
| 文書ごとの内容、開発者向けの書き分け、手順、例・図、編集、確認、保守 | [執筆の指針](references/writing.md) |

## 既存の形式と作業範囲

導入先が採用している文書形式とメタデータを尊重する。OKFの採用、検証日や有効期限の追加を一律に求めず、既存の情報を変えるときは用途と根拠を確認する。

OpenAPI、JSON Schema、Gherkinなどは、その形式の規約と既存の定義元に従う。計算の実行証明や、形式固有の詳細規約の整備は、このスキルの対象に含めない。Issue作成、PR、公開、マージなどは依頼範囲と対象リポジトリの運用に従う。
