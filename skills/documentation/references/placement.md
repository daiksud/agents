# 文書の読者と配置を決める

ここでの `docs/` は文書を整備するリポジトリ、スキルに同梱する `references/` はそのスキルの配布物を指す。依頼された範囲で、読者と目的に合う配置へ整理する。

## 読者を利用目的で分ける

| 読者 | 文書を使って行うこと |
| --- | --- |
| 利用者・ユーザー | プロダクトを選び、導入・利用・連携・運用する |
| 開発者・コントリビューター | プロダクトやリポジトリを変更・検証・保守する |

APIやライブラリを使うエンジニアは利用者に含める。同じ人が両方の役割を担う場合も、その文書で進める作業に応じて分類する。

## 基本となる配置

利用者向けは文書の種類で分類し、開発者向けは `docs/development/` にまとめる。読者名を先頭のディレクトリとして追加しない。各分類は必要になった時点で単一ファイルから始める。

`README.md` には目的・価値、主な用途、導入条件、利用開始の方法、詳しい文書への案内を書く。

| まず書くファイル | 分割が必要になったときのディレクトリ | 内容 |
| --- | --- | --- |
| `docs/concepts.md` | `docs/concepts/` | 考え方の理解に必要な概念、技術的な全体像、関係、背景 |
| `docs/tutorials.md` | `docs/tutorials/` | 学習用の環境で特定のゴールを達成する方法を学ぶ手順 |
| `docs/guides.md` | `docs/guides/` | 利用者自身の実装や環境で課題を解決する手順、運用、トラブル対応、移行 |
| `docs/references.md` | `docs/references/` | 公開API、CLI、設定などの正確な仕様 |
| `docs/development/policies.md` | `docs/development/policies/` | 現在の設計・開発方針、規約、制約、判断基準 |

開発環境、内部構造、責務、テスト、CI、リリース、保守の説明は `docs/development/` 内に置く。開発者向けの概念説明やチュートリアルも同じ場所に置き、各文書を単一ファイルから始める。利用者向けの分類をすべて複製することは求めない。

## 開発者向けの話題と配置

開発者が作業で知りたいことに応じて、必要な内容から書く。次のファイル名は例とし、単一ファイルで書き始める。

| 開発者の疑問 | ファイルの例 | 書く内容 |
| --- | --- | --- |
| 開発を始めるには何が必要か | `docs/development/setup.md` | 必要なツールとバージョンの参照元、環境の準備、起動・ビルド・最初のテスト、準備ができたことの確認方法 |
| どこを変更すればよいか | `docs/development/architecture.md` | 全体構造、構成要素の責務、依存関係、データや処理の流れ、変更が影響する範囲 |
| 変更するときに何を守るか | `docs/development/policies.md` | 現在の設計・開発方針、規約、制約、判断基準、守るべき互換性 |
| 変更をどう確かめるか | `docs/development/testing.md` | テストの種類と対象、必要な環境・データ、実行方法、期待する結果、CIで確認されること |
| どう配布し、問題に対応するか | `docs/development/release.md` | リリース条件、実行手順、成果物、公開後の確認、失敗時の対応 |

`CONTRIBUTING.md` は開発参加の入口として、変更提案やPRの出し方を案内する。詳しい作業は `docs/development/` の該当文書へつなぐ。有効な既存の配置を使い、同じ案内を複数作らない。

## 単一ファイルから必要に応じて分ける

小さな説明は、目的が合う既存ページの節としてまとめる。新しい文書が必要なら単一ファイルで書く。分類を埋めるための空ページや、すべての機能に対応する文書一式を作らない。

内容が増え、話題ごとに独立して探す必要が出たら、拡張子を除いた同名のディレクトリを作って分割する。例えば `docs/development/policies.md` を、必要に応じて `docs/development/policies/testing.md` や `docs/development/policies/release.md` に分ける。

分割した文書にも同じルールを適用する。その文書の内容が増えて分割が必要になった時点で、さらに階層を深くする。固定の文字数や将来の増加予測だけを理由に分割せず、読者が情報を探し、理解や作業を進めやすいまとまりを保つ。既存の分割構成が読者の目的に合っている場合は活かす。

## 配置に迷う場合

| 内容 | 配置の判断 |
| --- | --- |
| APIの使い方と公開仕様 | 手順は `docs/guides.md`、正確な仕様は `docs/references.md` |
| ソースからインストールするために必要なビルド | 利用者の導入手順として `docs/guides.md` |
| 実装を変更し、テストを追加・実行する手順 | `docs/development/testing.md` |
| 利用者が管理する環境のバックアップやアップグレード | `docs/guides.md` |
| 新しいバージョンをビルド・配布する開発側の作業 | `docs/development/release.md` |
| 利用者と開発者が参照する公開契約 | 一か所で管理し、両方の文書から参照する |

上の配置例も単一ファイルから始め、分割済みなら対応するディレクトリ内の文書を使う。

`AGENTS.md`、スキーマ、設定ファイル、公開APIのdocstringなどは、ツールや利用者が必要とする位置で管理する。ディレクトリ分類に合わせるために、読み込まれる位置や生成元を変えない。

## 現在の説明と判断の経緯を分ける

文書には現在の利用・開発・保守に必要な情報を書く。理解や利用判断に必要な仕組みの目的、価値、理由も含める。採用・変更時に比較した案、採否の理由、経緯、当時の調査・検証結果はPR・コミットに残す。

例えば「意図しない変更を適用前に把握できるよう、差分の確認と適用を分ける」は現在の概念説明に含める。「一括実行する案と比較し、今回の変更で分離する方式を採用した」という判断は変更の記録に残す。確認できない経緯を推測で補わない。

## 出典を説明の近くに置く

現在の説明を裏づける資料は、該当箇所にリンクや脚注として示す。版・章・ページ、対象バージョン、適用範囲が意味を左右する場合は、その条件も残す。外部資料が定めることと、このプロジェクト独自の方針を区別する。

出典をまとめるためだけの `skill-sources/` 分類は設けない。既存の出典文書を整理するときは、そこにしかない現行の規則や制約を使用箇所に移し、必要な出典を対応する説明へ統合する。必要な著作権・ライセンス・帰属表示を残してから、重複する文書と案内を整理する。

過去の調査や採用経緯はGit履歴で参照できるようにする。すべてを新しいPRへ転記することは求めない。過去の資料から重要な理由を移す場合は、今回行った調査や検証として扱わない。現在も説明の正確さに関わる未確認の範囲や制約は文書に残す。

## 実行指示と保守資料を分ける

スキルやエージェントへの指示は、実行時に必要な情報を配布物の中で読める構成にする。

- 基本規則は指示の読み込み先に置き、詳しい手順や例を必要な場面で読む同梱資料に分ける。
- 各スキルの `references/` や `assets/` はそのスキルに同梱する。実行に必要な情報をリポジトリの `docs/development/` へ移さない。
- 人がリポジトリを開発・保守するための説明は `docs/development/` に置く。
- 同梱資料へのリンクは配布後も成立するファイル相対パスにし、外部資料は完全なURLで示す。

## 既存文書を移動・整理する

1. 読者、目的、現在必要な内容、他の文書や生成元との重複を確認する。
2. 依頼された範囲で配置と役割を決め、必要な内容と出典を移す。
3. 参照元のリンク、frontmatter内のパス、目次、サイトのナビゲーションを更新する。
4. 移動先と対応中のバージョンで必要な情報を確認してから、重複・不要となった文書を整理する。

移行ガイド、利用者向けのリリースノート、対応中の旧バージョンの手順は、現在の利用に必要な情報として扱う。文書を移しただけで内容の再検証が済んだとは報告しない。
