## 読者と到達点を決める

読者の前提知識、達成したいこと、読み終えた後に理解・実行できることを確認する。必要に応じて、既存のIssue、問い合わせ、文書へのフィードバックから、説明が不足している箇所を探す。

1ページに一つの主な目的を持たせ、読者の疑問や行動を表す見出しを付ける。冒頭には目的、対象範囲、必要な前提を示す。既存の説明で足りる場合は参照し、必要な文書だけを作る。

機能仕様を除き、各分類はまず単一ファイルで書く。例えば、利用者向けの概念は `docs/concepts.md`、開発方針は `docs/development/policies.md` から始める。内容が増えて分割が必要になったら同名のディレクトリを作り、話題ごとのファイルへ分ける。さらに必要になった時点で階層を深くする。分割は主目的や手順のまとまりに合わせ、開発者向けの内容は `docs/development/` 内に保つ。機能仕様は[専用の配置と書き方](#利用者に提供する機能の振る舞いを書く)に従う。

## 文書の種類に合わせて内容を選ぶ

コンセプトと手順書の指針は、[『エンジニアのためのドキュメントライティング』](https://pub.jmam.co.jp/book/b622627.html)第2章の本文 pp.53–59 を基礎とする。各節に参照範囲を示し、リファレンスと共通の執筆・保守については、このスキルの実務上の指針を定める。

### コンセプト：考え方を理解する

一つの中心的な考え方に絞り、冒頭で紹介する。利用者がツールを理解するための背景と技術的な全体像を、次の内容から必要に応じて説明する。

- 中心となる概念と、関連する概念との関係。
- 構成要素やデータの扱われ方など、仕組みの概要。
- 現在の仕組みの目的、利用者にとっての価値、利用場面、その仕組みや方針である理由。
- その考え方を実践するチュートリアルやガイドへの案内。

説明する範囲を絞り、複数の大きな話題を詰め込まない。ここまでの構成は書籍 pp.53–55（概念の説明とテンプレート、範囲の絞り込み）を基礎とする。

このスキルでは現在の理解や利用判断に必要な理由を文書で説明し、採用・変更時の比較や経緯をPR・コミットに残す。

### チュートリアル：体験を通して学ぶ

学習用の環境で、特定のゴールを達成する方法を学べる内容にする。学習目標、完了時にできること、前提条件、環境と準備を先に示す。必要に応じてテストデータやツールを用意し、一連の手順、途中と完了時の結果、次に学ぶ内容を説明する。

10手順以上になったら、ユースケースの複雑さや学習内容の詰め込みを見直す。10手順は上限ではなく、長さは学習のまとまりに応じて決める。ツールの簡素化や自動化が学習を助ける場合は改善案として示す。書籍 p.56（学習環境、準備、手順数の目安）を基礎とする。

### ハウツーガイド：現実の課題を解決する

利用者が自分の実装や環境で、具体的な課題を解決できる内容にする。導入、設定、運用、トラブル対応、移行など、扱う作業に合わせて次の構成を使う。

1. 概要：解決する課題と、作業の全体像を示す。
2. 前提条件：事前の作業、依存関係、必要なシステムやパッケージのバージョンを示す。
3. 手順：行動、必要な選択や分岐、結果の確認を示す。必要に応じて復旧や後片付けも含める。
4. 次のステップ：続けて行う作業や関連文書へ案内する。

この目的と構成は書籍 pp.57–58（実際の課題を扱うガイドとテンプレート）に基づく。前提とする知識や技能は、作業に必要なものだけを具体的に示す。目的に不要な見出しや内容は追加しない。

できるだけ1ページで作業を完了できるようにする。扱う作業に必要な操作手順はガイド内に置き、背景や詳しい仕様は参照先へ案内する。関連情報や次のステップへのリンクは末尾にまとめることを基本とする。この構成は書籍 pp.58–59（ページのまとまりとリンクの配置）に基づく。

### リファレンス：正確な仕様を調べる

利用者が必要な仕様を見つけられるよう、項目の構成を揃える。対象に応じて、入力・出力、型、許容値、既定値、制約、エラー、対応バージョン、互換性を示す。

実装やスキーマなど、仕様を定義している情報と照合する。生成される文書は生成元を更新する。仕様と利用例を区別し、例だけでは伝わらない条件や制約を明示する。

## 開発者が変更と保守を進められるように書く

この節では開発者向けの執筆指針を定める。初めて参加した人や、その領域を初めて担当する人が、構造とルールを理解して変更・検証・保守を進められるように書く。言語やGitの基本知識は前提にしても、プロジェクト固有の事情は説明する。

文書の種類ごとの書き方を、開発者の目的に合わせて使う。

- コンセプトでは構成要素の責務、依存関係、変更が影響する範囲を説明する。全体を理解するための関係や境界を示し、コードから分かる細部は実装を参照する。
- チュートリアルでは練習用の小さな変更を通して、実装とテストの進め方を学べるようにする。
- ハウツーガイドでは開発環境の準備、テストの実行、リリースなどの前提条件、操作、結果の確認を示す。
- リファレンスでは開発用コマンド、内部の設定項目、拡張時の契約などを、実装やスキーマの定義と揃えて示す。

これらは開発者向けの話題として `docs/development/` 内に置き、扱う話題に合うファイル名を付ける。

次の表は架空の設定管理CLIについて、構造・開発方針・機能仕様・手順・採用経緯を書き分けた例である。ファイル名は `docs/development/` 内の例を示す。

| 記録先と役割 | 記載例 |
| --- | --- |
| `architecture.md`：現在の構造 | 差分の計算処理が変更内容を作り、適用処理が管理対象へ反映する。CLI層は引数を受け取り、それぞれの処理を呼び出す。 |
| `policies.md`：開発時のルールと判断基準 | CLI固有の引数処理と表示を、差分計算や適用の処理から分ける。変更時もコア処理をCLIの入出力に依存させない。 |
| `features/preview.feature.md`：利用者に提供する振る舞い | 差分の表示では、現在の設定と指定した設定の違いを示し、管理対象の設定を変更しない。この規則を具体的な値を使うシナリオで示す。 |
| `testing.md`：実行と確認の手順 | 機能仕様のシナリオに沿ってテスト用の設定と管理対象を準備し、差分表示を実行する。表示内容と実行後の状態を、仕様に示す期待結果と照合する。 |
| PR・コミット：比較と採用経緯 | 確認と適用を一度に行う案も比較し、変更内容を確認する機会を確保するため、操作を分ける案を採用した。操作回数が増える点は受け入れた。 |

現在の仕組みを理解し、変更を判断するために必要な理由は文書に含める。開発時の判断基準は `policies.md` に、利用者に対して保証する振る舞いは機能仕様に、テストの準備と実行・確認の方法は `testing.md` に書く。

開発者が作業で詰まる箇所や、繰り返し説明している内容から書く。小さな説明は目的が合う既存ページの節に加え、独立した文書が必要になったら単一ファイルを作る。内容が増えて独立して参照する必要が生じたら、主目的や手順のまとまりを保って分割する。公開仕様は一か所で管理し、開発者向け文書からも参照する。

## 利用者に提供する機能の振る舞いを書く

この節では機能仕様の執筆指針を定める。利用者に提供するツール、API、サービスの機能を、コントリビューターが実装・検証・保守の基準にできるように書く。プロダクトの開発・保守にだけ使い、利用者には提供しない補助スクリプトなどは対象に含めない。

APIやライブラリを使うエンジニアも、その機能については利用者に含める。機能を使うための案内は利用者向けに書き、ここで扱う機能仕様は提供する側のコントリビューターに向けて書く。

機能仕様は `docs/development/features/*.feature.md` に置く。単一ファイルから始める原則の例外として、最初の1機能から `features/` 内に機能ごとのファイルを作る。例えば、差分表示の仕様は `docs/development/features/preview.feature.md` に置く。

機能の目的と適用範囲を短い文章で示し、期待する振る舞いを規則と具体的なシナリオで説明する。シナリオには前提条件、利用者の操作や発生する事象、期待する観測可能な結果を書く。入力・出力、エラー、外から確認できる状態の変化などを具体的に示し、内部メソッドの呼出し順やデータ構造を写した仕様にしない。

構文は[Markdown with Gherkinの公式仕様](https://github.com/cucumber/gherkin/blob/main/MARKDOWN_WITH_GHERKIN.md)に従う。`Feature`、`Rule`、`Scenario` をMarkdownの見出しにし、`Given`、`When`、`Then`、`And` のステップをリストで書く。同じMarkdownに、理解に必要な説明も添える。

次は架空の設定管理CLIの例である。このガイドでは記法を見せるためにコードブロックで囲んでいる。実際の `.feature.md` では外側のコードブロックを付けず、見出しとリストを直接書く。

```markdown
# Feature: 適用前に設定の差分を確認する

利用者が変更内容を確認してから適用を判断できるようにする。

## Rule: 差分の表示では設定を変更しない

### Scenario: 現在値と指定値が異なる

* Given 管理対象のタイムアウトが30秒である
* And 設定ファイルにはタイムアウト60秒が指定されている
* When 利用者が差分の表示を要求する
* Then タイムアウトを30秒から60秒へ変更する差分が表示される
* And 管理対象のタイムアウトは30秒のままである
```

## 手順書では一つの手順に一つの行動を書く

チュートリアルとハウツーガイドに共通して、前提条件を先に示し、実行順に手順を並べる。一つの手順で一つの行動を説明し、必要な結果の確認を添える。操作に直接必要な説明を手順の近くに置き、背景の詳しい説明は分ける。この共通方針は書籍 pp.55–56（手順書の構成と行動の単位）に基づく。

## 例と図を説明に組み込む

以下はこのスキルで使う具体的な執筆・保守の指針とする。編集、コード例、図、フィードバック、品質、保守という対象範囲は、著者が公開する[目次](https://docsfordevelopers.com/table-of-contents/)の第4〜6章、第8〜11章も参考にする。

コードやコマンドの例には、必要な準備、入力、置き換える値、期待する結果を添える。そのまま実行できる例と説明用の断片を区別し、例の目的と重要な部分を本文で説明する。読者が理解して応用できる長さに絞る。

仕様や例を根拠と照合し、確認できていない動作や条件を補わない。言語や用語は対象リポジトリの規約に合わせ、同じ意味には同じ表現を使う。

構成要素の関係、処理の順序、状態の変化などを伝えるのに役立つ場合は図を使う。図が表す範囲と各要素を説明し、利用に必要な情報は本文にも残す。

## 推敲で理解と作業の完了を確かめる

次の観点を分けて読み直し、必要に応じて既存のレビュー手順で確認する。

- 正確さ：現在の仕様や振る舞いと一致しているか。
- 必要な内容：前提と説明が足りていて、読者が理解や作業を進められるか。
- 構成：必要な情報を見つけられ、適切な順序で読めるか。
- 明確さと簡潔さ：用語と指示が明確で、目的に必要な説明に集中しているか。

Markdownやリンクの検査は、内容の確認を補うものとして扱う。確認の実行は導入先の要件と依頼範囲に従い、実行による確認、静的な確認、未確認の範囲を区別して報告する。文書ごとの固定の報告書や追加の独立検証は求めない。

## 変更に合わせて文書を保守する

振る舞いが変わったら、影響する機能仕様、概念説明、手順、リファレンス、例、図、リンクを必要な範囲で同じ変更に含める。現在の説明を裏づける出典は、その説明の近くに示す。参照した版や適用範囲、必要な帰属表示を保つ。

文書を移動・削除するときは、参照元のリンクと、対応中のバージョンで必要な情報を確認する。移行ガイドやリリースノートには、利用者が必要な対応を判断するための情報を残す。不要になった説明や重複を整理し、現在も必要な内容を失わないようにする。

繰り返される質問、作業で詰まる箇所、文書へのフィードバックを改善に使う。ページ数や文章量を増やすことを目的にせず、読者の理解と目的の達成を助ける変更を選ぶ。
