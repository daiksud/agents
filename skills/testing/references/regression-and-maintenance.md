# 回帰テストと既存テストの改善

## 報告された不具合を再現する

報告から、発生時の状態、操作、期待した結果、実際の結果を取り出す。たとえば「一覧を保存し直すと古い項目が末尾に残る」なら、最初から空のファイルに保存しても症状は出ない。次のように、症状に必要な条件を残す。

1. 利用者と同じ保存操作で3件の一覧を保存し、同じ保存先に1件の一覧を上書きする。
2. 保存結果を読み、後から保存した1件だけが残ることを確かめる。修正前に実行し、失敗時に古い項目が残っていることを確認する。保存先が開けずに失敗した場合は、準備を直して再実行する。
3. 修正後に同じテストを実行し、期待した1件を読み出せることを確かめる。

修正前からテストが通るときは、再現に必要な入力や状態が抜けていないか、保存処理をテストダブルに置き換えていないか、期待値が古い項目の残存を検出できるかを調べる。修正前の状態を実行できなかった場合は、修正後に確かめた結果と、再現できなかった条件を記録する。

## ふるまいを保った変更でテストが壊れたとき

失敗した期待値を読み、それが変わったことで呼び出し元が何に困るかを考える。たとえば一覧を1件ずつ書く実装を一括書き込みに変えると、内部の書き込み回数を数えるテストは壊れる。上書き後の内容が契約なら、保存結果を読み、欠落・重複・古い項目を検出できる期待値にする。すでに同じ条件を確かめるテストがあれば、それを活かす。

テストが余分な手順を固定していても、一緒に有用な条件を守っている場合がある。成功時の呼び出し回数を外すときにも、「書き込みに失敗したら呼び出し元にエラーを返す」といった別の約束を確認するケースは残す。

## ときどき失敗するテストを調べる

再実行する前に、失敗した入力、期待値と実際の値、そのときの実行条件を控える。観測した違いを手掛かりに、一度に一つの条件を変えて原因を絞る。

| 手掛かり | 切り分け方 |
| --- | --- |
| 日付の変わり目で結果が変わる | 時計とタイムゾーンを指定し、境界の直前・直後で期待どおりかを調べる。 |
| ランダムな入力でだけ失敗する | 失敗した入力やシードを記録して再現し、失敗を起こす最小の入力を残す。 |
| 単独では通るが、まとめて実行すると失敗する | 直前のテストとの組み合わせや実行順を変える。並列でだけ失敗する場合は、同じ保存先やデータを同時に更新していないか調べる。 |
| 負荷が高いと完了を待てずに失敗する | 固定時間の待機を見直し、完了通知や観測できる状態の変化を期限付きで待つ。期限内の完了自体が契約なら、その期限を検証する。 |

再実行で通ったという観測だけでは、原因が解消したかは判断できない。たとえば並列実行で保存先が衝突していたら、各テストに個別の保存先を用意し、衝突が起きた実行条件でもそれぞれが期待どおりの内容を読み出せることを確かめる。
