## 変更単位と再現可能な検証

### 変更単位と検証

| 判断すること | 選び方 |
| --- | --- |
| Issueの分割 | 独立して価値・検証・統合を確認できる単位にする。一回のTDD反復や一つの具体例を、そのまま一つのIssueと同一視しない |
| 500行の目安 | レビュー負担の再検討に使う本環境の目安。BDD・TDD原典の規則ではなく、単なる行数で不可分な変更を分割しない |
| テスト層 | 速く原因を特定できる単体を優先し、実際の契約・接続・設定が原因なら最小の有効な統合テストを使う |
| 技術契約 | API応答、運用者への失敗通知など、読者に約束する観測可能な結果は共有仕様になり得る。内部の接続方式等の実装手順と区別する |
| 回帰修正 | 合意済み仕様が正しければ書き換えず、欠陥を再現する検証を足す。テストを通すために期待を変えない |

DDDのBounded Contextはモデルの意味の適用範囲、Subdomainは問題領域の区分、Gitリポジトリはコード管理単位です。用語・契約・所有・変更時の依存から対応を判断し、一律1対1をDDDの定義としません。テスト可能性と展開可能性を改善する際も、全体の書き直しではなく段階的な変更を選びます。

### 再現可能で目的に合うテスト

まず何の契約違反を検出したいかを決め、仕様から必要な入力と期待値を選ぶ。正常系・境界・失敗を確認できる最小のデータにし、実装の計算式を写して期待値を作らない。真偽値自体が契約なら真偽の検証を使い、物理的なアサーション数を一律に制限しない。

| 対象・条件 | 検証の組み立て方 |
| --- | --- |
| 状態や実行順に依存するテスト | ケースごとにデータ・共有状態を分離し、終了・失敗時にも後始末する。並行実行で識別子やファイルを共有しない |
| 時刻・乱数に左右される判定 | 制御可能な時計や乱数源を境界から渡し、境界値を再現する。乱数を使う探索では再現できる種や入力を記録する |
| 外部接続 | 単体では外部境界を隔離する。実際の接続・設定・契約が原因となる問題は有効な統合検証で確かめ、対象ロジックのモックへの置換で成功にしない |
| 非同期UI | 利用者が識別するrole・label等の安定した要素と、観測可能な状態を使う。固定sleepの延長で成功を待たず、条件待ちと失敗を検知するタイムアウトを使う。通信終了だけで画面の完了を代用しない |
| 性能が受け入れ条件である変更 | 合意した目標、負荷、データ量、測定期間・環境を先に揃える。空DBの単発測定を代表負荷での達成と扱わず、実測と未確認範囲を分ける |

時間経過そのものが契約の場合は、その契約を確認できる時計・環境を選ぶ。すべての待機を禁止したり、制御した時計だけで実環境の時間特性まで証明したりしない。UI失敗の画面・トレース等は原因を調べられる証跡として残し、機密情報が含まれる場合は記録範囲を制限する。

同じ条件で結果が揺れる不安定なテストでは、順序・状態・時刻・環境などの原因を調べる。再試行で成功した事実と原因の解消を区別する。CIの再試行・復旧は依存スキルtask-workflowの手順に従い、必要な統合検証を一律にマージ後へ送らない。

テスト層の比率・網羅率・mutation score・全APIの応答時間測定を共通の合否条件にしない。対象の契約・リスク・既存規約から選び、UIや性能の契約を持たない単純な関数へE2Eや負荷試験を追加しない。

検証の出典と採用判断は[一次資料](sources.md)に保持する。[^practice-sources]
