# GitHubで作業を完了する

変更・成果物作成を、GitとGitHubで計画からスカッシュマージ・main確認・作業環境の整理まで進める。相談・比較・説明・読み取りのみの調査にはこの作業サイクルを要求しない。調査から変更へ進む前に本スキルを適用する。

## 診断・計画だけの依頼

診断・導入計画の作成と記録が依頼の成果物なら、[診断・計画専用のIssue記録](references/planning.md#診断計画専用のissue記録)を使う。保存・再取得・表示確認・URLと本文の提示で完了し、導入未実施のIssueを開いたまま残す。実装開始の承認質問やブランチ・PR作成へ自動で進まない。以下の実行・マージの経路は、実装やファイル変更を依頼されたときに適用する。

## 計画から実行まで

文書のみ・小さな修正も、次の順序で進める。着手前に[計画と作業ブランチの準備](references/planning.md)を読む。

1. 読み取り調査で目的・成功条件・対象ファイル・変更内容・検証・完了条件を具体化する。
2. 計画をIssue本文へ保存し、再取得による本文一致と表示を確認して、URLと本文をユーザーに提示する。
3. 「この計画で実行・実装を開始してよいですか？」と質問し、明示的承認を待つ。Issue指定のゴール開始と承認の継続は[着手と計画](references/planning.md#着手と計画)に従う。
4. 承認後に差分・他セッションの作業を保護してブランチを準備し、承認済み範囲の編集・検証・コミット・PR・レビュー・マージまで進める。各操作の再確認は不要。
5. マージ後mainの必要検証と作業環境の整理まで確認して完了を報告する。

承認前は調査・計画調整・Issueへの記録と提示までとし、実装操作を開始しない。最初の依頼・Issueの存在・無回答を承認にしない。範囲追加・方針変更はIssue更新・本文提示・再承認を経る。関連の薄い追加依頼を受けた場合は[後続Issueの記録手順](references/planning.md#関連の薄い追加依頼の記録)を読み、記録だけを行って現在の承認済み作業を継続する。

ブラウザは利用者が求めた場合だけ、[Issue保存後のブラウザ起動](references/planning.md#issue保存後のブラウザ起動)に従って一度開く。URL提示・保存確認・計画承認は起動の有無によらず行う。

## 投稿・コミット・レビュー

- Issue・PR本文・コメントの新規投稿と更新前に[GitHub向けMarkdownの品質](references/markdown-quality.md)を読む。本文全体を共通rumdl設定で整形・チェックし、保存後に本文一致と表示を確認する。導入・ダウンロードの許可と失敗時対応も同資料に従う。
- Issueには目的・成功条件・計画・検証・完了条件、PRには変更内容・理由・検証結果を書く。固定見出し、不要な表・Alerts、空の節、「なし」の埋め草を要求しない。導入先の指定テンプレートに従う。
- Issue・PR番号やコミットSHAを日本語・句読点に続ける場合は、前後に半角スペースを入れ、コード記法で囲まず、投稿後に自動リンクを確認する。
- コミット前に[コミットメッセージ](references/conventional-commits.md)を読む。検証可能な小さい単位でコミットし、TDDの1サイクル、または文書変更の検証・コミットが完了したらプッシュする。
- PR作成・レビュー対応・リベース・マージ・整理の前に[レビューとマージ](references/review-and-merge.md)を読む。Copilot利用不能時のCodex切り替え、最新HEADの正常完了、過去を含む指摘の追跡、必須CI・承認・競合の確認も同資料に従う。
- レビュー自体を実行するときだけ `code-review` を適用する。依頼・指摘対応・完了判定は本スキルが担当する。

## 実行と検証

- コード変更では `bdd-tdd`、文書の作成・更新では `okf-docs` を適用する。プロジェクトのパスは作業対象リポジトリを基準とし、同梱資料のリンクは参照元ファイルを基準に解決する。
- 独立して検証できる小さな変更と短いブランチを計画し、[小さな統合単位と活動日](references/planning.md#小さな統合単位と活動日)に従って長期化の原因と次の統合単位を記録する。
- 成果物に対応する検証を計画どおり実行し、最終差分で依頼との一致・変更漏れ・既存機能への影響を点検する。文書は記述の整合性、パス・コマンドと差分の体裁も確認する。
- スキル判断の欠陥には、依存スキル `skill-creator` を読み、その作成・改善手順を適用する。未導入なら導入方法を確認して評価を未実施と記録する。再現入力と期待判断を模擬評価へ追加し、変更前後を同じ入力・基準の独立実行で比較する。形式検査やキーワード一致だけで判断品質を証明しない。
- 長い作業では判明したこと・残る課題・次の作業を共有する。失敗時は原因を調べ、根拠のある修正・代替手段を試す。同じ操作を理由なく繰り返さない。
- 変更作業中のmain失敗時は[統合後mainの確認と復旧](references/review-and-merge.md#統合後mainの確認と復旧)を優先し、正常化まで後続作業を進めない。復旧変更にも計画承認・レビュー・必須チェックを維持する。
- ユーザー判断や追加権限が必要なら、理由と対象操作を伝える。検証不能を成功にせず、完了範囲・未完了範囲・再開条件を報告する。

## 完了報告

対象Issue・PR、成果、検証とレビューの結果、マージ状態、main確認・同期とブランチ削除の結果、残る課題を示す。[レビューとマージ](references/review-and-merge.md)の完了条件を満たすまで、作業全体を完了としない。
