# GitHubで作業を完了する

明確な変更依頼・既に得た実行承認を保持し、Issueの計画記録から検証・レビュー・スカッシュマージ・main確認・整理まで担当する。計画だけの依頼や明示された停止条件を実装・マージの承認へ広げない。

## 工程ごとに読む資料

今の工程に対応する資料を読み、別工程の詳細はその工程へ進むときに読む。再開時は保存済みの計画・投稿・レビューと対象SHAを確認し、完了済みの操作を重複させない。

| Issueの作成・更新・提示、独立した後続依頼の記録 | [Issueの記録と提示](references/issue-recording.md) |

## 実行と検証の境界

- 文書のみ・小さな変更も、影響と不確実性に応じた読み取り調査で計画を具体化し、Issueへ保存・再取得して本文一致・表示を確認し、URLと本文を提示してから実装する。保存不能・未確認のまま編集しない。承認の要否は計画資料の条件で判断する。
- コード変更は依存スキル `bdd-tdd`、文書作成・更新は `okf-docs` を併用する。プロジェクトのパスは作業対象リポジトリ、同梱リンクは参照元ファイルを基準に解決する。
- スキル判断を変更するときは依存スキル `skill-creator` の作成・改善手順を使い、再現入力と期待判断を評価へ追加する。変更前後を同じ入力・基準の独立した模擬実行で比較し、形式検査やキーワード一致だけで判断品質を証明しない。未導入なら導入方法を確認し、未実施を記録する。
- 計画した検証を実行し、最終差分を依頼・関連機能・文書・パス・コマンドと照合する。検証可能な小さい単位でコミットし、TDDの1サイクルまたは文書の検証・コミット完了時にプッシュする。
- 変更作業中のmain失敗は[復旧手順](references/review-and-merge.md#統合後mainの確認と復旧)を優先する。自身の範囲内の回帰もレビュー・必須チェックを維持し、正常化まで後続作業を進めない。
- レビューを実行するときだけ `code-review` を適用する。レビュー依頼・指摘対応・完了判定の担当は本スキルとする。
- 長い作業は判明事項・残る課題・次の作業を共有する。失敗は原因と根拠のある代替手段を調べ、同じ操作を理由なく繰り返さない。ユーザー判断・追加権限が必要なら理由と対象を示す。

## 完了

診断・計画のみは、保存済みIssueのURLと本文、診断完了・導入未実施、未確認事項を示して終了し、Issueを開いたまま残す。実装開始の定型質問やPR作成へ進まない。

変更作業は最新HEADレビュー・要対応指摘ゼロ・必須CI・競合解消を満たしてスカッシュマージし、統合後mainの必要検証と同期・ブランチ整理まで確認する。レビュー利用不能時の切り替えと例外はレビュー資料に従い、保護設定を緩めない。明示された停止条件があれば、その到達点で終了する。

最終報告にIssue・PR、成果、検証・レビュー、マージ・main確認・整理の結果、残る課題を示す。未実施・取得不能を成功とせず、未完了範囲と再開条件を区別する。
