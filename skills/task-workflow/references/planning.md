## 計画と作業ブランチの準備

### GitHub Issueとタスク分割

- 変更・成果物作成のタスクをGitHub Issueに紐づけ、着手時に対象のIssue番号またはURLを明確にする。
- 対応するIssueがない場合は、後述の「関連の薄い追加依頼の記録」を除き、「🎯 目的」「✅ 目標」（検証・完了条件）「🛠️ 手段」（計画）の見出しで記載したIssueを作成してから作業を進める。
- Issue・Sub-issueを作成する場合は、タスク指示者をアサインする。
- タスク指示者のGitHubアカウントを特定できない場合はユーザーに確認し、認証ユーザーを無条件に指示者とみなさない。
- 現在のタスクを独立して計画・実行・検証できる作業に分割する場合は、親Issueに紐づくSub-issueとして作成する。
- 各Sub-issueに作業範囲、完了条件、依存関係を記載する。
- Sub-issueを作成しただけでは、そのタスクに着手しない。
- 分割タスクは、ユーザーが実施対象と順序を明示的に承認した範囲だけ、現在のセッションで直列に実施する。
- 別セッションに割り当てたタスクは、そのセッションに委ねる。
- Sub-issueへの着手前に、Issue・PR・作業ツリーから他セッションの着手状況を確認する。
- 別セッションが着手済みのタスクには、重複して取り組まない。
- 他セッションの着手状況を判断できない場合は、ユーザーに確認してから着手する。
- 分割後はSub-issueごとに計画・実行・検証を行い、親Issueの計画や検証だけで代替しない。
- 親Issueの完了は、各Sub-issueの完了と親Issue全体の完了条件を確認して判断する。

### 小さな統合単位と活動日

変更を早く検証してmainへ統合し、長期ブランチによる前提のずれを小さくする。[CIの原則](https://continuousdelivery.com/foundations/continuous-integration/)に基づき、次を計画に含める。

- 1つの変更を、独立して検証・レビュー・統合できる単位にする。ファイル数だけで分けず、利用者の目標と成功条件が確認できるまとまりにする。
- 変更作業を記録した日を活動日とし、活動日の毎日のmain統合、原則1活動日以内のブランチを目安にする。休日などの非活動日を作業遅延と決めつけない。
- Issueに作業開始日時、次の統合単位と検証方法を記録する。1活動日を超えた場合は、承認待ち・レビュー待ち・失敗調査など確認できた原因と次の統合単位を更新する。
- 承認・レビュー・CIを省略して目安を達成しない。期限だけを理由に未検証の変更をマージしない。
- 分割・順序・範囲が承認済み計画を変える場合は通常のIssue更新・再承認を行う。Sub-issueの作成を実行承認にしない。
- 着手時に統合先mainの必要な検証を確認する。mainが失敗中なら[復旧手順](review-and-merge.md#統合後mainの確認と復旧)を優先し、正常化するまで後続作業を開始しない。

活動日・滞留・レビュー待ち・検証時間・main復旧時間はIssue・PRと既存Actionsの時刻・URLを根拠に記録する。欠測、代用した時刻、未完了、利用不能を明記し、個人評価や単発比較からの改善効果の断定には使わない。プロジェクトごとの定義と実測値はプロジェクトの文書・Issue・PRに置き、共通スキルに個別実績を埋め込まない。

### Issueの記述

- Issueの作成・更新前に[GitHub向けMarkdownの品質](markdown-quality.md)に従い、本文全体を共通設定で整形・チェックする。投稿本文にOKFは付けず、保存後に本文と表示を確認する。
- 計画を作成するIssueとSub-issueはGitHub Flavored Markdownを積極的に活用し、「🎯 目的」「✅ 目標」「🛠️ 手段」の見出しで整理し、「目標」の下に「検証」「完了条件」、「手段」の下に「計画」の小見出しを設ける。
- [目的・目標・手段の整理](https://github.com/my-take-dev/inspired-mino-design-skills/blob/main/mino-doc/01-purpose-goal-means.md)に従い、目的には誰が実現したい状態・得たい価値を、目標には達成を判定できる仕様・制約・成功条件を、手段には目標を満たす作業・実装方法を書く。
- 「計画」には作業範囲・変更ファイル・実行手順を、「検証」には確認方法と実行結果（未実行ならその旨）を、「完了条件」には完了を判断するチェックリストを書く。
- Issue・Sub-issueの作成時はリポジトリのラベル一覧と説明を確認し、作業内容に合うラベルを設定する。
- 作業範囲が変わった場合はラベルも見直す。
- Emojiは見出しや状態の識別に使い、意味は本文でも伝える。見出しに付ける場合は「🎯 目的」のように見出し語を保持する。
- 並列の項目は箇条書き、順序のある手順は番号付きリスト、完了を追跡する項目はタスクリストで記載する。
- 変更対象と理由、検証項目と期待結果は表にまとめる。
- 承認待ち・対象外などの重要な制約はGitHub Alertsで明示する。その他の注意事項は、GitHub Alertsの `NOTE`・`TIP`・`IMPORTANT`・`WARNING`・`CAUTION` を内容に応じて使い分ける。
- 装飾や強調を一律に付けず、情報を探しやすくする箇所に使う。

### Issue保存後のブラウザ起動

利用者が保存したIssueをすぐ確認できるよう、次の対象操作ではOSの既定ブラウザでIssueを自動的に開く。起動の都度確認は求めない。

| 保存操作 | 自動起動 |
| --- | --- |
| 通常Issue・Sub-issue・計画なしの後続Issueの新規作成 | 開く |
| 既存Issueへの計画の保存・更新 | 開く |
| 既存Issueの参照・重複案内、コメント投稿、進捗・検証結果だけの更新、PR操作 | 開かない |

1. [GitHub向けMarkdownの品質](markdown-quality.md)に従い、本文全体を投稿前に整形・チェックして保存する。
2. 保存したIssueを再取得し、本文が整形済みファイルと一致することを確認する。保存失敗・本文未確認では起動しない。
3. 再取得したIssueのURLを、OS標準のURL起動手段で開く。macOSでは `open <URL>` を使う。URLは1つの引数として渡し、ブラウザ設定の変更や専用スクリプトの追加は行わない。
4. 同じ保存操作では一度だけ開く。新規Issueに計画を含めた場合も、作成と計画保存を理由に二重起動しない。復旧時は保存状態と起動済みかを確認し、成功済みの保存・起動を重複させない。
5. GitHubのレンダリング確認と、会話での保存済み本文・URLの提示も維持する。後続Issueの記録では下記のURL提示手順に従う。起動要求の成功だけを画面表示・目視確認の成功とは扱わない。

起動に失敗した場合は、Issueの保存成功と区別して起動失敗の理由・URLを伝える。起票や保存をやり直さず、起動だけの失敗で承認済み作業を停止しない。表示を確認できなければその範囲も報告する。

ブラウザ起動は計画・実装開始の承認ではない。通常の計画承認、範囲追加・方針変更の再承認を維持し、後続Issueを開いたことをそのIssueの計画・実装開始承認として扱わない。

### 関連の薄い追加依頼の記録

現在のタスクを継続しながら追加要望を失わず残すため、関連の薄い依頼の記録だけは、通常のIssueの計画形式と「着手と計画」の計画作成・承認フローの例外とする。

| 追加依頼と現在のタスクの関係 | 対応 |
| --- | --- |
| 現在の目的・成功条件を満たすために必要 | 承認済み範囲内なら反映し、範囲追加・方針変更なら「着手と計画」の計画更新・再承認手順を適用する |
| 独立した目的で、現在の目的・成功条件との関連が薄い | 別途対応する旨を伝え、以下の手順で独立した後続Issueへ記録する。現在のタスクは承認済み範囲で継続する |
| 関連性を判断できない | ユーザーに確認して回答後に振り分ける。回答に依存しない現在の作業は継続する |

1. 既存Issueを検索し、同じ依頼が記録済みなら重複起票せず既存IssueのURLを案内する。
2. 新規記録には依頼を端的に示すタイトル、依頼内容、「後続対応・計画未作成」の状態を記載する。仕様・実装方法・検証計画を推測して追加しない。現在のタスクのSub-issueにはせず、独立したIssueとして扱う。
3. 「GitHub Issueとタスク分割」「Issueの記述」に従い、指示者の特定・アサイン、リポジトリのラベル一覧と説明の確認・適切なラベル設定、本文全体の投稿前整形・チェック、投稿後の再取得・本文と表示の確認を行う。記録のために実装計画の承認を求めない。
4. 再取得による本文一致確認後、「Issue保存後のブラウザ起動」に従って一度開き、表示の確認とURLの提示を行う。記録しただけで計画作成・実装へ進まず、現在のタスクを承認済み範囲で継続する。

投稿失敗や保存未確認は起票済みと報告しない。保存成功を確認できても、起動・表示が未確認なら記録手順全体の完了とは扱わず、保存成功と失敗・未確認の範囲を分けて伝える。再開時に保存状態を確認して成功済みの操作を重複させない。回答や復旧に依存しない現在の作業は継続する。

後続Issueへの着手時、または明示的な計画作成依頼時に、元の要望を保持して「Issueの記述」「着手と計画」の通常形式で計画を作成・保存・再取得・提示する。計画作成だけの依頼を実装承認として扱わない。実装開始は通常の承認手順に従い、Issue指定のゴール開始による承認も同じ条件で適用する。

### 着手と計画

後続Issueの記録だけの場合は、上記「関連の薄い追加依頼の記録」に従う。それ以外は以下を適用する。

1. 実際のモードにかかわらず読み取り調査から始め、目的・成果物・制約・変更対象・変更内容・検証方法・完了条件を具体化する。文書のみ・小さな修正も計画と承認を省略しない。
2. 関連する指示と既存資料を確認し、新規作成・変更・削除するファイルと理由、実行順序を計画に記載する。成果物や範囲を左右する不明点は質問し、回答に依存しない読み取り調査は進める。
3. 「Issueの記述」に定めた見出しと書式で計画をIssue本文に保存する。既存Issueも今回実行する計画として内容を確認し、必要な更新を行う。更新前の本文を保持し、計画が変わる場合は変更前後と理由を本文の履歴欄に残す。
4. 保存したIssueを再取得して本文一致を確認し、「Issue保存後のブラウザ起動」に従って取得URLを一度開く。その後、GitHub上の表示（見出し・表・チェックリスト・Alerts・リンク）を確認し、URLと保存済み本文をユーザーに提示する。
5. ユーザーが `/goal #<Issue番号>` のようにIssueを指定してゴールを開始した場合（引用しただけの説明・相談を除く）は、そのIssueの実装開始を承認したものとして扱い、承認を再質問しない。それ以外は「この計画で実行・実装を開始してよいですか？」と質問し、明示的な承認を待つ。
6. 承認後に作業ブランチを準備し、承認済み範囲の編集・検証・コミット・PR・レビュー・マージを実行する。

> [!IMPORTANT]
> 承認前に許されるのは読み取り調査、計画の作成・調整、Issueへの記録と提示まで。コード・文書・評価データ・生成物の編集、ブランチ作成・切り替え、コミットなど実装を進める操作は行わない。Issueを指定したゴール開始指示を除き、最初の作業依頼、Issueの存在、無回答を承認とは扱わない。

- Issueへの保存が環境の制約でできない場合は、理由を伝え、保存・再取得・提示が可能になるまで実装へ進まない。
- 投稿・更新の反映に失敗した場合は、成功済みの操作を重複させずに再開する。
- ゴール開始による承認でも、Issueの読み取り、計画の具体化・保存・再取得・提示は省略しない。Issue本文に承認待ちと残っている場合は開始指示に基づいて更新し、実装へ進む。
- Issueを指定したゴール開始で得た承認は、そのゴールの自動継続や再開でも保持する。継続通知ごとに承認を求めない。ゴール開始の事実が確認できない継続通知だけを新規承認とは扱わない。
- `/goal #<Issue番号>` を引用した説明・相談はゴール開始指示ではない。承認は指定Issueの範囲に適用し、未承認のSub-issue、範囲追加、環境の権限付与まで広げない。
- 承認済み範囲内の細部は既存の慣習に合わせて判断し、各操作を再確認しない。
- 範囲追加や方針変更が必要なら、変更前の本文と変更理由を保持してIssueを更新し、「Issue保存後のブラウザ起動」に従って開き、変更後の本文とURLを提示して再承認を得る。変更された計画の実行は再承認まで待つ。
- 読み取りのみの相談・説明にはIssue作成と実行承認を要求しない。調査から変更に進む場合は上記の手順を適用する。

### ブランチの確認と準備

- 着手時に現在のブランチと作業ツリーの差分を確認する。
- 計画承認後、`main` の場合は、ファイル変更より先に `git switch -c <branch>` で作業ブランチを作成・切り替える。
- 計画承認後も環境の制約でブランチを作成できない場合は、理由を伝え、準備できるまで編集を開始しない。
- `main` 以外で自セッションが作成したと確認できないブランチは、変更前に作業ツリーの差分、最近のコミット、関連Issue・PR、`git worktree list` の結果を読み取り、今回のタスクとの関係と他セッションとの衝突の可能性を検証する。
- ブランチ名や差分がないことだけで、既存ブランチを利用してよいと判断しない。
- 既存ブランチを利用してよい根拠が得られない場合はユーザーに確認し、確認までは編集・ブランチ切り替え・stash・コミットなど状態を変える操作を行わない。
- 現在の作業ディレクトリの作業ブランチで変更・コミット・検証を行う。
- ブランチ名のプリフィックスは次の表に従う。

| 変更内容 | プリフィックス |
| --- | --- |
| 破壊的変更を含む機能追加 | `breaking/feat/` |
| 破壊的変更を含むバグ修正 | `breaking/fix/` |
| 破壊的変更を含まない機能追加 | `feat/` |
| 破壊的変更を含まないバグ修正 | `fix/` |
| ドキュメントのみの変更 | `docs/` |
| その他 | `build/`・`chore/`・`ci/`・`perf/`・`refactor/`・`revert/`・`style/`・`test/` のうち変更内容に合うもの |

その他のプリフィックスは [@commitlint/config-conventionalのtype定義](https://github.com/conventional-changelog/commitlint/blob/f4b108182e6d20eca52433135c7ba1675746318e/%40commitlint/config-conventional/src/index.ts#L24-L36) に従う。
破壊的変更に許可する型は、[コミットメッセージの指示](conventional-commits.md)に従う。

### 実行権限とツール呼び出し

- 計画にはコミット、プッシュ、PR作成、レビュー依頼・返信、修正、スカッシュマージ、mainへの切り替えとgit pull、マージ済みブランチの削除までの操作を含める。
- 計画時に、必要なコマンド、書き込み先、ネットワーク接続と現在の許可を確認し、不足する権限を明示する。
- Codexでコマンドの事前許可を準備する場合は、[Codexのコマンド事前許可](https://github.com/daiksud/agents/blob/main/docs/guides/codex-command-approvals.md)を参照する。
- 計画承認後は、承認済みの範囲をマージまで進め、各操作について再確認しない。
- 承認済みの範囲には、実施対象と順序が未承認のSub-issueを含めない。
- 計画の承認を環境の権限付与とみなさず、追加権限や範囲変更が必要な場合は理由と対象を示して確認する。
- 関連する読み取りや独立した確認は一度のツール呼び出しにまとめ、同じ情報を変化の根拠なく再取得しない。
- 権限昇格が必要なコマンドと通常権限で実行できるコマンドは、同じシェルコマンド列にまとめず、それぞれの権限で実行する。
- 結果に依存する操作は、前の操作の成功を確認してから実行する。
- レビューやCIの待機では、完了待機機能を利用するか確認間隔を空け、過剰なポーリングを避ける。
- ツール呼び出し回数の削減と実行表示の非表示を区別し、提供されていない表示制御を約束しない。
