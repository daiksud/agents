# 開発実践を診断し、導入を計画する

利用者へ価値を安全に届ける流れを調べ、最初に試す改善を具体化する。9概念を全部導入したという判定や、ツールの一括置換を目的にしない。

依存スキル `task-workflow` の診断・計画専用経路を使う。以下のリポジトリ・`docs/` は診断対象を指す。対象の共通指示・プロジェクト指示も確認する。

## 適用と範囲

1. 開発実践の現状診断・導入計画が依頼されていることを確認する。通常の修正や説明から本スキルを自動起動しない。
2. 対象リポジトリ、利用者の成果、アプリケーション・サービスと価値の流れ、制約を確認する。既存のIssueや診断があれば引き継ぐ。
3. 診断の範囲や優先順位を左右する目的が不明なら、人に確認する。回答に依存しない資料調査は進め、未回答を確定事項にしない。
4. [原則の関係](references/principles.md)と[証拠から導入計画を作る](references/assessment.md)を読んで診断する。定義や版差を検証するときは[一次資料と適用上の判断](references/sources.md)を使う。

## 証拠を集める

- リポジトリの文書・仕様・コード・テストだけでなく、履歴・実行済みCI・配布・障害の記録を調べる。
- 取得した証拠にパスまたはURL、対象SHA・日時・観測期間を付け、主張との対応を残す。
- 実践を確認できた範囲、根拠のある不足、未確認、理由のある適用外を分ける。取得不能は不足の立証ではない。
- 方針や設定があることと、実際にその方法で働いていることを区別する。テスト先行や関係者の合意は、成果物の存在だけから推測しない。
- 責任分担・文化・認知負荷は、担当者の経験と照合する。CODEOWNERSやディレクトリ構造だけで人やチームの状態を断定しない。

## 制約から改善を選ぶ

- 概念を指定された診断では、その範囲の不足・不明点と影響を整理する。包括的な診断では9概念を対象の流れに照らす。
- 関連観点は、依頼の目標への影響を証拠で説明できる範囲で調べる。追加の調査や成果物で依頼範囲を変える場合は確認する。
- 全項目の点数化や一律の成熟度判定をしない。
- 最も影響する制約から、独立して検証できる最初の小さな実験を選ぶ。
- 各候補に、期待する変化、順序・依存、担当する役割、受け入れ条件、検証方法と見直し条件を示す。担当者の合意や実施日は確認前に確定しない。
- 単独開発、複数チーム、レガシー、モノレポ等の条件に合わせる。4チームの新設や一律のサービス・リポジトリ分割を導入条件にしない。
- 指標を使う場合は対象・定義・期間・出典と欠測を明示する。少ないデータをゼロや改善効果に置き換えず、個人評価や固定Elite判定に使わない。

## 計画を記録して引き継ぐ

1. 証拠と未確認事項、改善の優先順位、最初の実験と検証を含むIssue本文を作る。詳しい内容は[計画の成果物](references/assessment.md#計画の成果物)に従う。
2. Issueの検索・保存・整形・再取得・表示確認と提示は `task-workflow` に従う。再診断では既存の根拠と判断変更の履歴を保持する。
3. 保存済みURLと本文を提示し、診断完了と導入未実施を区別する。導入未実施のIssueを閉じない。
4. 投稿禁止のモードや保存不能の場合は、未保存の本文案と理由・再開条件を提示する。保存済み・診断手順全体の完了とは報告しない。

このスキルはコード・CI設定・組織の変更、ブランチ作成、PR、マージを行わない。診断中にmainの失敗を見つけても、証拠と復旧の優先度を計画に記録する。実装を依頼された場合は、対象計画を引き継いで `task-workflow` の通常経路へ移る。
