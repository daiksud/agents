## ツールの選定

ビルド・lint・テスト・公開には導入先の既存コマンドと設定を使う。ランタイム・パッケージマネージャー・依存管理も既存の構成に合わせ、同じ用途のツールを重ねない。

| 用途 | 選定方針 |
| --- | --- |
| ワークフローの静的検査 | `actionlint` を使う。同じ検査を行う既存の構成があれば優先する |
| コミット形式の検査 | `commitlint` でConventional Commits形式を検査する。同等の既存ツールがあれば優先する |
| バージョン計算 | Conventional Commitsに対応する既存ツールを使う。なければ `semantic-release` などを選び、[計算規則](workflow-design.md#リリースバージョン)に設定を合わせる |
| セキュリティ検査 | 必要に応じて `zizmor` を使う |
| アクションの依存更新 | Dependabotなど、採用済みの更新手段にそろえる |
| デプロイ | 配備先に合う既存の展開手段を使う。CLIの成果物はActionsのArtifactsに保存する |
| リリース | 既存の公開・機能切り替え手段を優先する。CLIではGitHub Releaseを作成する |

コミット検査とバージョン計算で、typeと破壊的変更の解釈をそろえる。`!` と破壊的変更のフッターを認識するパーサーを使う。計算ツールの既定値には依存せず、`perf` のpatch更新など、採用した規則と異なる判定を設定で合わせる。

## ランタイムとランナー

JavaScript アクションの `runs.using` は、アクション内部のランタイムを表す。`setup-node` の `node-version` やアプリケーションの `engines` が指定するプロジェクトの実行環境とは別に扱う。内部ランタイムの警告だけを理由に、プロジェクトの Node.js やロックファイルを更新しない。

更新先は実際に使うランナーのバージョン、OS、アーキテクチャ、GitHub.com・GitHub Enterprise Server の対応範囲と互換性があるものを選ぶ。

## バージョン更新

- ツールのバージョンは既存の設定やロックファイルで固定する。ローカルとCIで共用するツールは同じ定義を使い、CI専用ツールはワークフロー側で固定する。アクションの参照は[安全性](hardening.md)の固定方法に従う。
- 公式の安定リリースから互換性のある更新先を選び、バージョンコメントと参照先を一致させる。古い例の SHA や固定された推奨メジャーバージョンをそのまま採用しない。
- 入力・出力・既定値・認証・キャッシュ・成果物の互換性を保つ。内部ランタイムだけの変更でも、アクション全体の動作が同じとは限らない。
- 複合アクションや再利用可能なワークフローの内部を含め、更新が必要な参照を小さな単位でそろえる。互換性の条件が違う呼び出し元まで一律に更新しない。
- 環境変数で警告を隠すことや、アクションが対応していない `runs.using` を宣言することを恒久対策にしない。
