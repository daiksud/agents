## Actionsと配備先の設定

- Actionsの実行許可を使用するアクション・再利用可能なワークフローとそろえる。`GITHUB_TOKEN` の既定権限は読み取りに絞り、組織・Enterpriseの制限と既存の保護を維持する。
- 配備先の保護や設定の分離が必要ならEnvironmentsを使い、配備ジョブの `environment` と対応付ける。配備を許すブランチ・タグと必要な承認を設定し、利用プランとリポジトリの公開範囲による制限を確かめる。
- 認証情報はSecrets、機密でない設定値はVariablesに保存し、必要なリポジトリ・環境で使う範囲に絞る。

## 権限とシークレット

- `permissions: {}` または必要な読み取り権限を基本とし、書き込み権限は必要なジョブだけに与える。実効権限はリポジトリ設定と呼び出し関係にも左右されるため、トリガー名だけで判断しない。
- シークレットは必要なジョブとアクションに限って渡し、ログ・成果物・キャッシュに残さない。マスク表示だけに頼らず、不要なチェックアウト認証の保持は `persist-credentials: false` で避ける。
- クラウドが対応する場合は OIDC で長期間有効なキーを減らす。`id-token: write` は必要なジョブに限り、クラウド側の信頼条件をリポジトリ・ブランチ・環境と必要な権限に絞る。

## 信頼境界と外部入力

- 信頼できない PR コードのビルド・テストは、隔離した最小権限の `pull_request` ジョブで実行する。`pull_request_target`、`workflow_run`、`issue_comment` の特権処理で、PR 由来のコード、ローカルアクション、設定、インストール時のスクリプトを実行しない。
- 認証情報の送信先、プラグイン、実行ファイルの探索パスは、信頼できる側の設定で管理する。データとして読み込むファイルでも、特権処理の設定を上書きできれば安全とはいえない。
- レビューによる実行許可は正確なコミット SHA に結び付ける。ラベルや実行承認を将来の変更への許可とみなさず、SHA の固定だけで内容の安全性を判断しない。
- `workflow_run` の実行元は許可したワークフローと起動イベント、リポジトリ、ref、SHA で識別する。ワークフロー名やブランチ名の一致だけでは信頼しない。
- PR の本文・ブランチ名・手動実行の入力などをコードへ埋め込まない。引用符で囲んだ環境変数や引数配列でデータとして渡し、`eval` などで再解釈しない。改行を含む値を `GITHUB_ENV`・`GITHUB_OUTPUT` に直接書かない。
- ランナーのラベルだけで提供元や隔離を判断しない。永続的なセルフホステッドランナーでは、前の実行の状態、認証情報、内部ネットワークを信頼できないコードと共有しない。一時的な登録だけではホストの初期化を保証できない。

## 依存と成果物とキャッシュ

- 外部アクションは採用済みロックファイルの対象にするか、公式リリースと対応する完全なコミット SHA に固定する。外部の再利用可能なワークフローは完全な SHA、コンテナはダイジェストに固定する。間接的な依存先と実行時のダウンロードも対象とする。
- 信頼できない成果物は実行ファイルや設定から離れた一時ディレクトリで扱う。展開先の外を指すパス・リンクや想定外のファイルを拒否し、特権処理で PR 由来のコードや設定を読み込まない。
- 成果物のデータはサイズ・スキーマ・型を限定する。そこに書かれたリポジトリや PR の識別子を書き込み操作の許可とみなさない。署名やダイジェストの一致だけでは内容の安全性を証明できない。
- 信頼度の低いキャッシュを、共有パスや広すぎる復元キーを通じて特権で実行しない。`permissions` だけでキャッシュの権限を制限できるとは限らない。対応環境では、必要に応じて呼び出し側のジョブの `cache-mode` を `read` または `none` に制限する。
