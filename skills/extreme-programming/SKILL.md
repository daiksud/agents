# 人間同士のペアでXPを実践する

二人の人間が対話しながら、共同でAIエージェントを使って開発する。AIエージェントはペアが判断するための情報を提供し、合意した指示に従って調査、実装、検証を行う。

合意した振る舞いを満たす最もシンプルな設計を選ぶ。今必要な理由を説明できない抽象化、拡張ポイント、設定項目は追加しない。要求をそのまま実現すると設計が過度に複雑になる場合は、利用者の目的と複雑さの原因を示し、範囲を絞る案やよりシンプルな実現方法を依頼者に提案して合意する。[Simplicity](references/values.md#simplicityシンプリシティ)

## ストーリーから最初のテストを選ぶ

「誰が、どんな状況で、何をできるようになるか」を一文で表す。既に合意したストーリーや仕様があれば使う。範囲が大きければ、利用者が一通り試せる最小の成果を切り出す。受け入れ条件は、操作と外から観察できる結果の組で表す。業務上の判断で結果が変わる場合は、具体例を示して依頼者に確かめる。

実装に入る前に、受け入れ条件を確かめる具体例をテストリストとして控え、その中から次に試す一つを選ぶ。作業中に新しい例が分かったらリストに加える。専用のファイルは必要ない。

| 変更の種類 | 最初に確かめること |
| --- | --- |
| 機能追加 | テストリストから代表例を一つ選び、利用者や呼び出し側が期待する結果をテストにする。 |
| 不具合修正 | 報告された条件を再現し、正しい結果を期待するテストが現在の実装で失敗することを確かめる。保存や通信が原因なら、その不具合を検出できる境界で試す。 |
| 振る舞いを保つリファクタリング | 変更対象の振る舞いを既存テストが捉え、そのテストが通ることを確かめる。保護が足りなければ、維持したい振る舞いをテストで押さえてから構造を変える。 |

## ペアでAIへのプロンプトを決める

ペアプログラミングは必ず二人の人間で行う。実装に関する判断と知識を、変更前から対話を通じて共有する。AIエージェントはペアの共通の開発ツールであり、ドライバーにもナビゲーターにもならない。AIエージェント同士や人間とAIエージェントの一対一の作業はペアプログラミングとみなさない。

- **ドライバー**はナビゲーターと対話しながらAIへのプロンプトを決め、合意したプロンプトを入力する。
- **ナビゲーター**は要求の解釈、次に試す例、設計や実装の方針についてドライバーと考え、プロンプトを一緒に組み立てる。

最初に受け入れ条件とテストリストを共有し、どの例から始めるかをペアで決める。AIへの指示を送る前に、その目的、期待する結果、変更の範囲についてペアで合意する。AIの出力、差分、テスト結果を二人で確認し、何が分かったかを話し合い、次のプロンプトを決める。役割は適宜交代する。

AIエージェントは、ペアが合意した指示の範囲で作業し、結果や新たに分かったことを共有する。次のテストの選択や重要な設計判断が必要になったら、選択肢と根拠を示し、ペアの指示を受けて進む。実装後のPRレビューやAIによるレビューを人間同士のペアプログラミングの代替にしない。

二人の参加が確認できない場合は、このスキルによるペアでの実装を開始しない。AIエージェントを代役に立てたり、ペアで作業したことにしたりしない。

## テストを一つずつ通し、設計を整える

テストは利用者や呼び出し側から観察できる振る舞いと契約を検証する。内部構造、内部メソッドの呼び出し順序などの実装方法には依存させない。外部とのやり取り自体が契約である場合は、そのやり取りを検証する。テストを通すために期待値やアサーションを弱めたり、実装の結果をそのまま期待値にしたりしない。

振る舞いを追加・修正するときは、次のサイクルを繰り返す。構造だけを変えるときは、対象の振る舞いを守るテストが通った状態から Refactor に進む。

1. **Red** — 次の例を一つだけ実行可能なテストにし、期待する振る舞いが欠けているために失敗することを確かめる。環境やテストデータに原因があれば、それを直して再実行する。
2. **Green** — 新しいテストと、それまで通っていた関連テストを通す最小限の変更を加える。途中で気づいた別の条件はテストリストに加える。
3. **Refactor** — テストが通る状態で名前や責務を見直し、同じ業務ルールの重複があればまとめる。別の理由で変わる処理は、見た目が似ているだけで共通化しない。改善する箇所があれば一つずつ変えて再実行し、次の例に移る。

たとえば「参加者は空席のある回を予約できる」というストーリーでは、まず「残り1席で申し込むと、自分の予約一覧にその回が載る」をテストして通す。次のサイクルで「満席の回に申し込むと満席と表示され、自分の予約一覧は変わらない」を確かめる。両方が通った時点で空席判定が表示と受付に重複していれば、一つにまとめて再実行する。最後に、参加者が使う予約操作から両方の受け入れ条件を満たすことを確かめる。

テストの選び方は Kent Beck の [Canon TDD](https://newsletter.kentbeck.com/p/canon-tdd) を参照。

## 小さく統合する

ストーリー全体の完了を待たず、独立して統合できる小さな変更が完成したら、必要な検証を行い、プロジェクトの統合手順と依頼の範囲に沿って早期に統合する。共有のコードのビルドやテストが失敗した場合は、次の変更より復旧を優先する。原因を特定して直すか、プロジェクトの手順に沿って該当する変更を戻す。[Continuous Integration](references/primary-practices.md#continuous-integration継続的インテグレーション)

合意した例を満たしたら、どの振る舞いをどのテストで確かめたか、未確認の条件があれば何が残ったかを伝える。
