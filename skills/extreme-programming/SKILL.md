# XPで機能を実装する

## ストーリーから最初のテストを選ぶ

「誰が、どんな状況で、何をできるようになるか」を一文で表す。既に合意したストーリーや仕様があれば使う。範囲が大きければ、利用者が一通り試せる最小の成果を切り出す。受け入れ条件は、操作と外から観察できる結果の組で表す。業務上の判断で結果が変わる場合は、具体例を示して依頼者に確かめる。

| 変更の種類 | 最初に確かめること |
| --- | --- |
| 機能追加 | 受け入れ条件から代表例を一つ選び、利用者や呼び出し側が期待する結果をテストにする。ほかの例は次の候補として控える。 |
| 不具合修正 | 報告された条件を再現し、正しい結果を期待するテストが現在の実装で失敗することを確かめる。保存や通信が原因なら、その不具合を検出できる境界で試す。 |
| 振る舞いを保つリファクタリング | 変更対象の振る舞いを既存テストが捉え、そのテストが通ることを確かめる。保護が足りなければ、維持したい振る舞いをテストで押さえてから構造を変える。 |

## エージェント同士でペアを組む

複数エージェントで作業できる環境では、同じストーリーにドライバーとナビゲーターを置く。最初に受け入れ条件、次のテスト候補、そのうちどれから始めるかを共有する。

- **ドライバー**は選んだテストと実装を編集し、失敗の内容や通るようになった差分をナビゲーターに見せる。
- **ナビゲーター**は実装中の差分とテスト結果を読み、見落とした条件、次に試す例、今の設計を単純にできる箇所を具体的に返す。編集はその時点のドライバーに任せる。

二者で実際の結果を見て、次のテストに進むか、設計を整えるかを決める。役割を交代するときは、最後に通ったテストと残りの例を引き継ぐ。単独で作業する環境でも、以下のサイクルを使う。

## テストを一つずつ通し、設計を整える

振る舞いを追加・修正するときは、次のサイクルを繰り返す。構造だけを変えるときは、対象の振る舞いを守るテストが通った状態から Refactor に進む。

1. **Red** — 次の例を一つだけ実行可能なテストにし、期待する振る舞いが欠けているために失敗することを確かめる。環境やテストデータに原因があれば、それを直して再実行する。
2. **Green** — 新しいテストと、それまで通っていた関連テストを通す最小限の変更を加える。途中で気づいた別の条件は候補に戻す。
3. **Refactor** — テストが通る状態で名前や責務を見直し、同じ業務ルールの重複があればまとめる。改善する箇所があれば一つずつ変えて再実行し、次の例に移る。

たとえば「参加者は空席のある回を予約できる」というストーリーでは、まず「残り1席で申し込むと、自分の予約一覧にその回が載る」をテストして通す。次のサイクルで「満席の回に申し込むと満席と表示され、自分の予約一覧は変わらない」を確かめる。両方が通った時点で空席判定が表示と受付に重複していれば、一つにまとめて再実行する。最後に、参加者が使う予約操作から両方の受け入れ条件を満たすことを確かめる。

合意した例を満たしたら、プロジェクトで使っている統合手順と依頼の範囲に沿って変更をまとめる。どの振る舞いをどのテストで確かめたか、未確認の条件があれば何が残ったかを伝える。テストの選び方は Kent Beck の [Canon TDD](https://newsletter.kentbeck.com/p/canon-tdd) を参照。
