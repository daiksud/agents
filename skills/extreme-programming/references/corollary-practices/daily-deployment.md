# Daily Deployment（デイリーデプロイ）

本番に出せる小さな変更を日々届け、実際の利用結果を次の開発に反映する。統合したコードがテストを通った後にも、稼働データ、利用者の操作、配備手順で初めて分かる問題がある。変更をためるほど、その問題がどの変更で生じたかを調べにくい。速く繰り返せるビルドと、配備後に影響を観測して復旧できる手段が土台になる。[10分ビルド](../primary-practices/ten-minute-build.md)

## 本番で確かめたいことを一つ決める

予約期限の表示を改善した日は、配備が成功したかに加えて、期限切れを理由に入力をやり直す利用者が減ったかを見る。異常が生じたときに直前の版へ戻せる変更なら、原因を調べる間も利用者が操作を続けられる。戻しにくいデータ変更を伴う場合は、先に旧版でも読めるデータ形式を配備するなど、切り戻せる単位を作る。日々の配備回数と、利用者が改善を確かめられた回数は分けて捉える。
