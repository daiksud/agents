# Diversity（多様性）

同じ仕様を読んでも、製品を使う人、障害を復旧する人、コードを書く人では気づくことが違う。判断を固める前に、失敗したときに困る当事者の視点を入れる。見解が割れたら、各人が想定した条件と結果を具体例にして並べると、一方の発言を退けずに違いを調べられる。

## 一括取込の「成功」を確かめる

開発者は千行のファイルを読み終えれば成功と考え、窓口担当者は不備のある行だけを直してやり直したいと考えていたとする。重複登録への問い合わせを受ける保守担当者にも参加してもらい、「一行だけ不備があり、同じファイルを再送した」を一緒にたどる。そこから、登録済みの行を判別できることと、不備を直す場所が分かることを受け入れ条件にできる。実際の担当者が追加の口頭説明なしで再取込を完了できるかを試す。
