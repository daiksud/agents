# 一般的なタスクの進め方

調査、実装、修正、文書作成などの作業依頼に適用する。
コードの追加・変更・修正を伴う場合は、[プログラミングを行うタスクの指示](./programming-tasks.instructions.md)も適用する。

## GitHub Issueとタスク分割

- すべてのタスクをGitHub Issueに紐づけ、着手時に対象のIssue番号またはURLを明確にする。
- 対応するIssueがない場合は、目的と完了条件を記載したIssueを作成してから作業を進める。
- 独立して計画・実行・検証できる作業に分割する場合は、親Issueに紐づくSub-issueとして作成する。
- 各Sub-issueに作業範囲、完了条件、依存関係を記載する。
- 分割後はSub-issueごとに計画・実行・検証を行い、親Issueの計画や検証だけで代替しない。
- 親Issueの完了は、各Sub-issueの完了と親Issue全体の完了条件を確認して判断する。

## Issueの記述

- IssueとSub-issueはGitHub Flavored Markdownを積極的に活用し、目的、作業範囲、完了条件を見出しで整理する。
- Emojiは見出しや状態の識別に使い、意味は本文でも伝える。
- 並列の項目は箇条書き、順序のある手順は番号付きリスト、完了を追跡する項目はタスクリストで記載する。
- 比較や対応関係など、複数の項目を同じ観点で読む情報は表にまとめる。
- 注意事項や重要な制約は、GitHub Alertsの `NOTE`・`TIP`・`IMPORTANT`・`WARNING`・`CAUTION` を内容に応じて使い分ける。
- 装飾や強調を一律に付けず、情報を探しやすくする箇所に使う。

## 着手と計画

- タスクに着手したら、自動切り替えが可能な環境ではPlanモードへ切り替える。
- 自動切り替えができない環境では、その制約を伝え、調査と計画を先に行う。
- すべてのタスクで、成果物、制約、変更対象、変更量、完了条件、検証方法を具体化してから実行に進む。
- 依頼から成果物、制約、完了条件を把握し、関連する指示と既存の実装・資料を確認する。
- 依頼内容から変更が必要なファイルを調査し、新規作成・変更・削除するファイルと、それぞれの変更理由を計画に記載する。
- 成果物や変更範囲を左右する不明点は質問し、回答に依存しない作業は進める。
- 容易に修正できる細部は既存の慣習に合わせて判断し、結果に影響する仮定は伝える。

## 実行と障害対応

- 作業依頼は成果物の作成と検証まで進め、提案や計画だけで終えない。
- 変更前に既存の差分を確認し、依頼と関係のない変更を上書き・取り消ししない。
- 依頼の達成に必要な範囲を変更し、無関係な改善は別の提案として扱う。
- 長い作業では、判明したこと、残る課題、次に行うことを区切りごとに共有する。
- 追加の指示を受けたら、進行中の作業と計画に反映する。
- 失敗した場合は原因を調べ、根拠のある修正や代替手段を試す。同じ操作を理由なく繰り返さない。
- ユーザーの判断や追加の権限が必要になった場合は、必要な理由と対象の操作を具体的に伝える。
- 障害で進められない場合は、完了した範囲、未完了の範囲、再開に必要な情報や対応を報告する。

## 検証と完了

- 成果物に対応する検証を、計画で定めた方法で実行する。
- 文書のみの変更では、記述の整合性、記載したパスやコマンド、差分の体裁を確認する。
- 最終的な成果物と差分を確認し、依頼との一致、変更漏れ、既存機能への影響を点検する。
- 完了条件を満たし、対応する検証に合格したことを確認して完了を報告する。
- 最終報告には対象のIssueまたはSub-issue、成果、実行した検証と結果、残る課題を含める。
- 検証を実行できなかった場合は、その理由と未確認の範囲を伝え、検証済みとして扱わない。
