## 共通の作業原則

プロジェクト固有の指示も確認する。
以下の `docs/` は作業対象リポジトリを指し、`~` はユーザーのホームディレクトリを指す。スキルは下記の配布先から読む。

### 作業スキルの読み込み

| 条件 | 着手前に読むスキル |
| --- | --- |
| 変更・成果物作成、Issue対応、PR・レビュー対応 | `~/.agents/skills/task-workflow/SKILL.md` |
| コードの追加・変更・修正 | `~/.agents/skills/bdd-tdd/SKILL.md` |
| コードレビューの実行時だけ | `~/.agents/skills/code-review/SKILL.md` |
| 文書の作成・更新 | `~/.agents/skills/okf-docs/SKILL.md` |
| 開発実践の現状診断・導入計画を依頼されたとき | `~/.agents/skills/engineering-assessment/SKILL.md` |

- 複数の条件に該当するときは、それぞれのスキルを適用する。
- 相談・比較・説明・読み取りのみの調査には、Issue作成・PR・マージの作業サイクルを要求しない。
- 調査から変更・成果物作成へ進むときは、着手前に対応するスキルを読む。
- 文書を作成・更新するときは `okf-docs` に従い、通常概念・索引/履歴・固有形式を区別する。出典、信頼・鮮度、更新時の記録保持も同スキルで確認する。

### 設計判断の前提

ソフトウェア、機能、モジュール、クラス、メソッドは、アクターが望む状態を実現するための手段として扱う。

| 区分 | 定義 |
| --- | --- |
| 目的 | アクターが実現したい状態、得たい価値、解消したい困りごと。 |
| 目標 | 目的を達成したと判定するための、観測可能な仕様、制約、成功条件。 |
| 手段 | 目標を満たすためのシステム、機能、モデル、コード、技術。 |

- 設計判断を始める前に、対象アクターと目的・目標・手段を分離して明確にする。
- 設計判断は、どの目的・目標を満たすための手段を選ぶのかと対応づける。
- 目的・目標・手段に設計判断を左右する不明点がある場合は、ユーザーに確認してから判断する。

### 価値の流れと学習（DevOps・Lean）

以下は日々の判断の軸とし、通常の変更で毎回9概念の全面診断を要求しない。概念の関係や出典を確認するときは `~/.agents/skills/engineering-assessment/references/principles.md` を読む。

- DevOpsでは、企画・開発・検証・運用を通じた利用者の成果に対して責任を共有する。
- 品質・セキュリティ・信頼性を、引き渡し後の検査だけに委ねず設計と日常作業に組み込む。
- Leanでは、利用者へ価値が届くまでの待ち・仕掛かり・手戻りを含む流れ全体を改善する。
- 改善は最も影響する制約に対する小さな実験として、期待する変化と見直し条件を決める。
- 人を責める最適化や過負荷を避け、現場の知識と持続可能な働き方を尊重する。

### 共有理解と検証（BDD・ATDD・TDD）

- BDDでは、関係者の異なる観点からルール・具体例・未回答の質問を整理し、共有理解をつくる。
- ATDDでは、対応する実装より先に受け入れ条件を具体化し、期待する成果の確認に結びつける。
- コード変更にはTDDを適用し、テストリストから一つずつ失敗・最小の成功・整理を反復する。
- ドメインロジックの変更では、実装コードより先にBDDのfeature文書を保存する。

具体例・テスト層・既存仕様やリファクタリングの扱いは `bdd-tdd` に従う。文書やテストの存在だけをBDD・ATDD・TDDの実践の証拠にしない。

### 継続的デリバリー（CD）

- 検証済みの変更を必要なときに安全に届けられる状態を維持する。
- 同じ成果物を環境間で昇格させ、構成の版管理・再現可能な配布・復旧方法を確認する。
- 配備と利用者への公開を区別し、公開判断は業務上の条件と既存の承認に従う。

CDはすべての変更を自動で本番へ出す継続的デプロイメントを必須にしない。

### チームの境界と相互作用（チームトポロジー）

- 価値の流れを妨げる依存とチームの認知負荷を、実際の担当者の経験から確認する。
- 責任範囲と協働・サービス提供・支援の関係を、規模と現在の制約に合わせて進化させる。
- 4つのチーム型を必須の組織図として当てはめない。

### 設計方針（DDD）

- ドメイン駆動設計（DDD）を設計の軸とする。
- 業務上の問題領域であるサブドメイン、モデルの意味が通用する境界づけられたコンテキスト、コードの管理単位であるリポジトリを区別する。
- コンテキスト・モジュール・サービス・リポジトリ・所有チームの対応と選択理由を明示する。
- 境界を越える依存・契約・翻訳を確認する。
- コンテキスト・リポジトリ・チームなどに一律の1対1対応や分割を要求しない。
- 対象ドメインの用語、ルール、不変条件、モデルの境界を確認してから設計する。
- ドメインロジックをUI・通信・永続化などの技術的な処理から分離し、ドメインのルールをモデルに表現する。

### ユビキタス言語

- 用語集を `docs/glossary.md` に作成し、用語、ドメイン上の定義、適用するモデルの境界、コード上の名称を記載する。
- 同じモデルの境界内では、featureファイル・テスト・実装の用語を用語集に揃える。
- 用語の追加や意味の変更が生じた場合は、用語集と関連するfeatureファイル・テスト・実装を合わせて更新する。
- 用語の意味が曖昧な場合はユーザーに確認し、推測した定義を確定事項として用語集に記載しない。

### 計画と実行承認

- 目的・範囲が明確な変更依頼を実行承認として扱う。読み取り調査で計画を具体化し、Issueへ保存・再取得・提示してから実装する。既に得た承認を再質問しない。
- 相談・調査・計画のみの依頼では、その成果物までで終了し実装しない。Issueの存在や無回答だけを実行承認にしない。
- 同じ目的・成功条件を満たす手順、対象ファイル、分割・順序の調整は、理由と計画を更新して継続する。
- 目的・成果・受け入れ条件の変更、外部への影響の増加、未合意の業務判断、追加権限が必要な場合は、具体案と理由を提示して確認する。回答に依存しない作業は進める。
- 依頼の検証に必要な既知の依存は一時ディレクトリや専用環境へ導入できる。グローバル設定変更・追加権限・費用発生は確認する。
- 明示された停止条件・Plan Mode・環境の制約を優先する。実行承認は環境の権限付与を意味しない。
- Issue記録、計画だけの完了、承認の継続と確認が必要な場合の手順は `task-workflow` に従う。

### 変更保護と作業範囲

- 変更前にブランチと差分を確認し、依頼と関係のない変更を上書き・取り消ししない。
- 他セッションの作業を尊重し、別セッションに割り当てたタスクには着手しない。
- 依頼された範囲はマージまで進め、各操作の再確認はしない。目的内のSub-issueの分割・順序は判断し、別の目的や他セッションのタスクへ承認を広げない。
- 継続・再開でも依頼と承認を保持し、確認が必要な条件は「計画と実行承認」に従う。

### 継続的インテグレーション（CI）と復旧

- 変更担当者はPRのマージ後も、統合後mainの必要な検証結果を確認するまで担当する。PR側の成功だけで完了にしない。
- 独立して検証・統合できる小さな変更で進め、活動日の毎日の統合を目安にする。期限のために必要な承認・レビュー・CIを省略しない。
- 変更作業中にmainの失敗を検出したら、通常作業より正常な状態への復旧を優先する。mainが正常に戻るまで後続作業を進めない。
- 原因変更の復旧はrevertまたは最小修正のPRで行い、通常の必要な承認・レビュー・必須チェックを維持する。外部障害で変更不要なら、根拠を記録して同じmain SHAの必要検証を再実行する。復旧手順は `task-workflow` に従う。
- 探索・受け入れ検証で見つかった欠陥は再現可能な小さい検証へ反映し、影響・確認できた原因・検出できなかった理由・復旧・残る改善を記録する。
- 実測値はIssue・PRに根拠とともに残し、欠測をゼロや成功に置き換えない。個人評価や単発の改善効果の断定に使わない。

### 完了条件

- 変更・成果物作成はIssueに紐づけ、計画、検証、コミット、PR、レビュー、CI確認、スカッシュマージまで進める。
- コミットは英語のConventional Commits形式とし、破壊的変更を許可する型は `feat`・`fix` のみとする。
- 最新コミットのレビュー完了、対応が必要な指摘ゼロ、CIパス、コンフリクトゼロをマージ条件とする。
- 通常は最新コミットのCopilot Approveを得る。証拠付きで利用不能を確認した場合だけ、`task-workflow` の代替レビューへ追加確認なしで切り替える。Codexは最新HEADの正常完了と過去を含む要対応指摘ゼロを条件とし、リポジトリの必須承認・保護設定は緩めない。
- 検証不能・権限不足・外部サービスの制約を成功とみなさず、完了範囲と未完了範囲、再開条件を報告する。
